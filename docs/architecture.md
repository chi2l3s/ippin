# Архитектура IPPin

Проект состоит из одной библиотеки и тонкой CLI-точки входа. Один Cargo-пакет достаточен для текущего размера: отдельные workspace-crates и обобщённые репозитории добавили бы переходы между слоями без независимых компонентов.

| Модуль | Ответственность |
| --- | --- |
| `config` | Схема и валидация конфигурации, пресеты, атомарное хранилище, блокировки |
| `transport` | Неизменяемый маршрут, HTTP CONNECT/SOCKS5, DNS нужного семейства, TLS, HTTP-клиент |
| `checker` | Ограниченный по размеру и времени запрос Cloudflare trace, строгий разбор ответа, интерфейс `IpProbe` |
| `gate` | Сверка с привязанным IP и отмена допущенных сессий |
| `pac` | Генерация PAC и сопоставление доменов |
| `proxy` | Входящий HTTP, CONNECT, потоковый forward/reverse proxy, монитор, локальные control endpoints |
| `service` | Готовность, запуск и штатная остановка процесса через случайный токен |
| `platform` | Windows PAC, восстановление настроек, автозапуск и безопасный запуск процесса |
| `main` | Разбор команд, связывание компонентов, журналы, сигналы и коды завершения |
| `ui` (бинарный файл) | Оформление терминала, цвета, состояния и вывод без ANSI в pipe; сетевая библиотека от него не зависит |

## Путь запроса

1. Сервер проверяет HTTP-форму и целевой адрес. Локальные маршруты отделены от запросов в абсолютной форме.
2. `Gate::admit` сериализует измерение через `IpProbe`; положительного кеша нет. Измеритель использует тот же `Transport`, что и запрос.
3. При совпадении выдаётся токен текущего поколения сессий. Соединение устанавливается по зафиксированному маршруту; отмена проверяется и во время установки.
4. CONNECT передаёт байты в обе стороны. HTTP передаёт запрос и ответ потоками, без накопления всего тела в памяти. Драйвер исходящего HTTP-соединения живёт до окончания потока или отмены.
5. Ошибка любого измерения отменяет всё текущее поколение. Успешное последующее измерение допускает новые сессии; отменённые соединения не оживают.

Монитор вызывает тот же механизм с интервалом 2 секунды. Проверки последовательны, поэтому обнаружение не имеет жёсткого SLA в 2 секунды. Само измерение ограничено двумя попытками по 3 секунды. Допуск на основе пробного запроса не доказывает атомарную неизменность сетевого маршрута; подробные границы указаны в README.

## Время жизни ресурсов

Перед настройкой PAC сервер захватывает lock единственного экземпляра и привязывает сокет. Запись `instance.json` не считается признаком готовности: управляющая команда требует корректного HTTP-ответа с токеном и PID.

Корневой `CancellationToken` закрывает обработчики клиентов, туннели и монитор. Задачи сервера отслеживаются через `TaskTracker`; штатная остановка ждёт их завершения с ограничением времени. Файловый lock остаётся захваченным до завершения очистки PAC и состояния.

Одновременно допускаются до 256 локальных HTTP-соединений и 256 туннелей. Входящие HTTP-заголовки ограничены буфером 32 КиБ и ожиданием 10 секунд. Установка TCP/TLS ограничена 5 секундами на этап, ожидание исходящих HTTP-заголовков — 120 секундами; длительные тела и SSE продолжаются до закрытия/отмены. Trace-ответ ограничен 16 КиБ; CONNECT-ответ upstream — 16 КиБ. Автоматических повторов полезных HTTP-запросов и переходов по redirect нет.

## Межпроцессное состояние

`config.lock` защищает весь цикл чтение → изменение → проверка → запись. Временный файл в том же каталоге синхронизируется и заменяет целевой файл атомарно. Ошибка валидации оставляет старую конфигурацию. `instance.lock` запрещает второй процесс даже на другом порту для того же каталога.

PID нужен для диагностики и сопоставления ответа. Остановка посылает HTTP POST с 256-битным случайным токеном. Если endpoint не отвечает, но lock захвачен, команда сообщает ошибку. Если lock свободен, устаревшая запись удаляется. Чужой процесс по PID никогда не сигнализируется.

Windows-процесс создаётся через `CreateProcessW` без наследования дескрипторов и с `CREATE_NO_WINDOW`. Это предотвращает наследование каналов вывода скрипта и его зависание в ожидании EOF. Участки `unsafe` ограничены Windows API и снабжены объяснениями инвариантов. Правила наследования описаны в [документации Microsoft](https://learn.microsoft.com/en-us/windows/win32/procthread/creating-processes).

## Тестирование

Модульные тесты покрывают конфигурацию, домены, PAC, trace, допуск и протоколы upstream. `tests/proxy.rs` проверяет реальный HTTP/CONNECT-трафик, потерю IP и отмену потоков на локальных сокетах. `tests/cli.rs` проверяет исполняемый файл, параллельные записи конфигурации, занятый порт, фоновый процесс и подделку состояния.

Тесты не меняют рабочие настройки прокси ОС. Реальную интеграцию PAC/браузеров и маршрутизацию конкретного VPN необходимо проверять отдельно. CI/workflow-конфигурация сама по себе не означает, что удалённые сборки уже выполнены.
