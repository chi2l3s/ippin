# Переход с Go на Rust

## Порядок обновления

1. Старым исполняемым файлом выполните `ippin service uninstall`; убедитесь, что старый ручной процесс тоже остановлен. Rust-процесс не управляет старым Go-процессом по PID.
2. Сохраните копию `~/.ippin/config.json`. Если Go-версия меняла системный прокси, проверьте его настройки: она не сохраняла полную резервную копию.
3. Соберите Rust-версию через `cargo build --release --locked` или установите `cargo install --path . --locked`. Убедитесь через `ippin --version`, что запускается версия 2.0.0.
4. Проверьте `ippin mode`, используя явный loopback-прокси, и заново выполните `ippin lock` при включённом VPN.
5. Выполните `ippin start` и проверку через `curl -x`; на Windows затем можно выполнить `ippin service install`.

Имена и расположение полей Go-конфигурации сохранены. Домены приводятся к нижнему регистру, убираются `*.` и конечная точка, дубликаты исключаются. Неправильные IP, домены, порты и неподдерживаемые proxy URL теперь возвращают ошибку; исправьте их до запуска. Поддерживаются только локальные HTTP/SOCKS5-прокси без аутентификации.

Старый `ippin.pid` больше не используется. Rust сохраняет `instance.json` с токеном и использует файловую блокировку. Старые `ippin.log` доступны через `logs`; новые журналы ротируются по дням. `start -p` меняет порт только текущего процесса. Изменения настроек требуют перезапуска сервера. Сценарии, полагавшиеся на код 0 при ошибке, должны учитывать ненулевой код завершения.

## Исправленные дефекты

| Дефект Go-версии | Решение |
| --- | --- |
| Auto-маршрут заново выбирался для проверки IP и каждого соединения | Один маршрут на время запуска, общий для измерения и передачи |
| Положительный кеш IP мог пропускать запрос после смены сети | Измерение перед каждым допуском |
| Монитор закрывал только CONNECT, оставляя HTTP/API-потоки | Общие поколения отмены для всех допущенных соединений |
| Пустой/неправильный trace мог вернуть `(nil, nil)` и вызвать панику в `lock` | Типизированный IP, явная ошибка, проверка статуса и лимит тела |
| Данные после HTTP CONNECT терялись из-за отброшенного буфера | Чтение ровно заголовка и сохранение ранних туннельных байтов |
| SOCKS5 неполно проверял версию, reserved byte и address type | Строгая проверка ответа и кодирование IPv4/IPv6/имени |
| Домены могли вставить JavaScript в PAC; совпадение суффикса было неоднозначным | Валидация DNS, JSON-экранирование, граница DNS-метки |
| Локальные пути могли перехватывать forward-запросы с тем же путём | Сначала разбор абсолютной формы, затем локальных маршрутов |
| Заголовки соединения и proxy credentials уходили дальше | Удаление стандартных и перечисленных в `Connection` заголовков |
| Ошибки CLI и сохранения замалчивались | Контекст ошибок, ненулевые коды и атомарные обновления |
| PID-файл мог указывать на другой процесс; старт не проверял готовность | Аутентифицированный control endpoint и lock экземпляра |
| PAC устанавливался до успешного bind и прежние настройки терялись | Сначала bind; резервная копия и штатное восстановление |
| Настройки PAC принудительно переписывались каждые 10 секунд | Отсутствие периодического вмешательства в системные настройки |
| Журнал рос без ограничения числа файлов, `logs` читал его целиком в память | Дневная ротация до 7 файлов и ограниченная очередь строк при чтении |
| Windows-потомок мог удерживать унаследованные дескрипторы | Скрытый запуск без наследования handles; регрессионный тест |
| Установщик выбирал только AMD64 и не проверял архив | AMD64/ARM64, точное имя asset и обязательный SHA256 |

Перенос и набор тестов не являются доказательством отсутствия всех возможных ошибок. В частности, периодические внешние IP-проверки не дают абсолютной гарантии отсутствия сетевой утечки.

## Предложения по развитию

1. **Самое существенное для строгой защиты — enforcement на уровне ОС.** Windows Filtering Platform / nftables / pf или отдельный network namespace с разрешённым выходом только через VPN устраняют класс проблем, который нельзя закрыть измерением IP. Нужны отдельный проект правил, права ОС и тесты восстановления, чтобы не заблокировать пользователю сеть.
2. **Привязка к явному upstream вместо `auto` в рабочей конфигурации.** Это уже доступно и делает маршрут понятным при старте и после отказа клиента.
3. **Наблюдение за изменением интерфейсов/маршрутов ОС.** Может ускорить отмену сессий между измерениями; не заменяет сетевую политику.
4. **Настоящий supervisor.** Windows Service / systemd / launchd могут перезапускать процесс после аварии и ограничивать ресурсы. Текущий пользовательский автозапуск выполняет только запуск при входе.
5. **Проверка с реальными VPN-клиентами.** Отдельные стенды для смены ноды, TUN, split tunneling, IPv6, потери Cloudflare и поведения браузеров при отказе PAC дополнят локальные тесты.

Эти пункты не включены молча: первые, третий и четвёртый меняют модель работы с ОС, права или способ установки.
